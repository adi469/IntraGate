IntraGate Architecture

IntraGate is an enterprise-grade Single Sign-On (SSO) and Reverse Proxy Gateway. It intercepts requests bound for internal applications and enforces OAuth2 authorization using Microsoft Entra ID (OIDC), keeping access completely centralized, secure, and audit-logged.

Design Principle
IntraGate is engineered with zero hardcoded credentials and absolute separation of concern. All secrets are derived strictly from environment variables at startup, and session tokens are encrypted symmetrically using AES Fernet at rest.

System Architecture

IntraGate is split into two primary components running concurrently in the same runtime:

  • User Portal & Reverse Proxy: Serves user requests on port 9000. Validates user sessions and handles low-latency proxy forwarding to registered internal microservices.
  • Admin Panel: Runs on port 8585, strictly bound to localhost (127.0.0.1) to prevent direct internet exposure. Features local administrator auth, TOTP Multi-Factor Authentication, configuration registry, and CSV/PDF audit log exports.

Data Flow Overview

Request Authentication & Forwarding Sequence
Client Request -> IntraGate (Port 9000)
    │
    ├── [1] Check Session Cookie (intragate_sid)
    │     ├── Missing/Expired -> Redirect to Microsoft Entra ID Login
    │     └── Active -> Validate in Postgres Session Table & Decrypt Tokens
    │
    ├── [2] Audit Log Extraction (Trusted Proxy Check & IP Sanity)
    │
    ├── [3] Sanitization (Strip incoming X-Gateway-User-* & session cookies)
    │
    └── [4] Forward Request with Identity headers to Upstream app

Deployment Guide

IntraGate is fully containerized and easily deployed using Docker and Docker Compose. We provide automated database migrations and configuration validation out-of-the-box.

To deploy using Docker Compose, create a directory and write the following docker-compose.yml file:

docker-compose.yml 
version: '3.8'

services:
  database:
    image: postgres:15-alpine
    container_name: intragate-db
    restart: unless-stopped
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: intragate_gateway
    volumes:
      - db-data:/var/lib/postgresql/data
    networks:
      - gateway-network

  gateway:
    image: intragate:latest
    build: .
    container_name: intragate-service
    restart: unless-stopped
    ports:
      - "9090:9000"           # User Portal exposed publically
      - "127.0.0.1:8585:8585" # Admin Panel bound to localhost only
    environment:
      - DATABASE_URL=postgresql+asyncpg://postgres:${POSTGRES_PASSWORD}@database:5432/intragate_gateway
      - GATEWAY_SECRET_KEY=${GATEWAY_SECRET_KEY}
      - GATEWAY_ENCRYPTION_KEY=${GATEWAY_ENCRYPTION_KEY}
      - GATEWAY_HOST=0.0.0.0
      - GATEWAY_PORT=9000
      - ADMIN_PORT=8585
      - TRUSTED_PROXIES=${TRUSTED_PROXIES}
    depends_on:
      - database
    volumes:
      - uploads-data:/app/data/uploads
      - .env:/app/.env
    networks:
      - gateway-network

volumes:
  db-data:
  uploads-data:

networks:
  gateway-network:
    driver: bridge

Create a .env file in the same directory containing your deployment secrets. See the Environment Reference for generation guidelines.

Start Command 
docker-compose up -d --build

For native local development, install python requirements and expose parameters locally.

System Setup 
# Install required system packages
pip install -r requirements.txt

# Export environment variables
export POSTGRES_PASSWORD="YourDbPassword"
export GATEWAY_SECRET_KEY="32-byte-hex-session-signing-secret"
export GATEWAY_ENCRYPTION_KEY="32-byte-url-safe-base64-fernet-key"
export DATABASE_URL="postgresql+asyncpg://postgres:${POSTGRES_PASSWORD}@localhost:5432/intragate_gateway"

# Run migrations and start app
python run.py

Admin Panel Access

To prevent malicious threat actors, automated scanners, or brute-force bots from querying or attacking the management endpoints, the IntraGate Admin Panel binds exclusively to 127.0.0.1:8585 (localhost). This means it does not listen on any public network interface on the server. Below are the detailed procedures for administrators to access this secure interface.

Understanding the Loopback Bind

When running IntraGate via Docker Compose, the service binds using the port mapping 127.0.0.1:8585:8585. This maps port 8585 of the container to port 8585 of the host server's local loopback interface (127.0.0.1). Even if the host server has a public IP address (e.g., 203.0.113.10), the admin port is completely inaccessible from the outside network.

Verify Loopback Bind on Server
To verify that the admin port is restricted only to the loopback interface on your hosting server, run the following command as root/sudo: 
ss -tulpn | grep 8585
The output should show: 
LISTEN  0  512  127.0.0.1:8585  0.0.0.0:*
If it shows *:8585 or 0.0.0.0:8585, the port is exposed publicly and you must adjust your docker-compose file or system firewall rule immediately.

Method 1: SSH Port Forwarding (Recommended)

SSH port forwarding (SSH tunneling) creates an encrypted secure channel from your local administrator workstation to the hosting server. All traffic is tunneled through the SSH connection.

Open a terminal (or Command Prompt / PowerShell on Windows) and run the following command:

SSH Tunnel Command 
ssh -L 8585:127.0.0.1:8585 -N -f username@your-server-ip

Parameters Explained:

  • -L 8585:127.0.0.1:8585: Directs SSH to listen on port 8585 on your local workstation and forward it to 127.0.0.1:8585 on the remote server host.
  • -N: Tells SSH not to execute any remote command. This is useful when only forwarding ports.
  • -f: Backgrounds the SSH process once authentication is completed.

Once authenticated, open your web browser on your local workstation and navigate to http://127.0.0.1:8585.

If you use PuTTY on Windows, configure port forwarding as follows:

  1. Open PuTTY and input your server's host name or IP address in the Session panel.
  2. In the left tree view, navigate to Connection -> SSH -> Tunnels.
  3. In the Port forwarding configuration fields:
    • Source port: Input 8585 (your local workstation port).
    • Destination: Input 127.0.0.1:8585 (the server's local loopback port).
    • Ensure the radio buttons are set to Local and Auto.
  4. Click the Add button. You should see L8585 127.0.0.1:8585 listed in the *Forwarded ports* list box.
  5. Go back to the Session screen, save your session, and click Open to log in.
  6. Keep the PuTTY terminal window open. In your local web browser, visit http://127.0.0.1:8585.

If you use MobaXterm, use the graphical Tunneling tool:

  1. Click the Tunneling button in the top menu bar.
  2. Click New SSH tunnel.
  3. Configure the tunnel settings:
    • Forwarded port (local): Input 8585.
    • SSH Server: Input your server IP address and SSH username/port.
    • Destination server (remote): Input 127.0.0.1 and Port 8585.
  4. Save the settings, then click the **Start** (play) icon next to the created tunnel.
  5. Open your local browser and navigate to http://127.0.0.1:8585.

Method 2: Reverse Proxy (Traefik or Nginx) with CIDR IP Whitelist

If your organization requires accessing the admin panel directly via an HTTPS domain (e.g. admin.intragate.dev) without creating SSH tunnels, you must place a reverse proxy in front of the localhost binding and protect the route using an IP Allowlist middleware to prevent unauthorized public access.

Write a Traefik HTTP router configuration incorporating the ipAllowList middleware:

dynamic_config.yml 
http:
  routers:
    intragate-admin:
      rule: "Host(`admin.intragate.dev`)"
      service: admin-service
      entryPoints:
        - websecure
      tls:
        certResolver: myresolver
      middlewares:
        - admin-ip-whitelist

  middlewares:
    admin-ip-whitelist:
      ipAllowList:
        sourceRange:
          - "192.168.1.0/24"      # Corporate office subnet
          - "203.0.113.50/32"     # Admin remote home IP (static)

  services:
    admin-service:
      loadBalancer:
        servers:
          - url: "http://127.0.0.1:8585"

Write an NGINX server block using the allow and deny directives:

nginx.conf 
server {
    listen 443 ssl http2;
    server_name admin.intragate.dev;

    ssl_certificate /etc/letsencrypt/live/admin.intragate.dev/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/admin.intragate.dev/privkey.pem;

    location / {
        # Strict IP Access restriction block
        allow 192.168.1.0/24;    # Corporate office subnet
        allow 203.0.113.50;      # Admin remote home static IP
        deny all;                # Drop TCP connections from anywhere else

        proxy_pass http://127.0.0.1:8585;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

Environment Reference

IntraGate enforces strict sanity checks on environment variables at start. The gateway immediately fails to start if any required variable is missing or insecure.

Variable Name Required Format & Example Purpose & Integrity Check
GATEWAY_SECRET_KEY Yes Min 32-char hex string
openssl rand -hex 32		 Used for session cookie signing, anti-CSRF token verification, and state parameter generation. Must be at least 32 characters long.
GATEWAY_ENCRYPTION_KEY Yes 32-byte URL-safe base64 key
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"		 Used for symmetric encryption of sensitive credentials (e.g. Entra ID Client Secrets) and session tokens in PostgreSQL. Must be a valid Fernet key.
POSTGRES_PASSWORD Yes Alphanumeric string (min 16 chars) Connection password for PostgreSQL database. Avoid simple strings.
DATABASE_URL Yes SQLAlchemy connection string
postgresql+asyncpg://postgres:pwd@db:5432/db		 Database connection URL for SQLAlchemy. Uses asyncpg driver.
TRUSTED_PROXIES No Comma-separated IPs
10.0.0.1,192.168.1.10		 Proxy IP addresses allowed to forward the X-Forwarded-For header. Unwhitelisted IPs trigger log warnings and are ignored to prevent IP spoofing.
GATEWAY_DEV_MODE No true / false (Default: false) Enables local SSO bypass using ?mock=true query parameter during testing. MUST be false in production.

Session Management

IntraGate features distributed, PostgreSQL-backed sessions instead of local memory stores. This architecture ensures high availability and horizontal scalability behind load balancers.

Token Encryption At Rest

When a user completes SSO login, IntraGate receives an access_token and id_token from Entra ID. To minimize data leakage risk in the event of database compromise, these values are symmetrically encrypted via Fernet before persisting:

Encryption Routine (app/session.py)
def encrypt_tokens(user_dict: dict) -> dict:
    d = dict(user_dict)
    fernet = Fernet(GATEWAY_ENCRYPTION_KEY)
    if d.get("access_token"):
        d["access_token"] = fernet.encrypt(d["access_token"].encode()).decode()
    if d.get("id_token"):
        d["id_token"] = fernet.encrypt(d["id_token"].encode()).decode()
    return d

Session Life Cycle & Purging

A background clean-up task (session_cleanup_worker) runs periodically inside the main process loop. It deletes expired admin and user sessions from the PostgreSQL database using dynamic timeouts configured by the administrator:

  • Absolute Lifetime Check: Sessions are deleted if created_at < time.time() - session_lifetime_hours.
  • Inactivity Timeout Check: Sessions are invalidated if last_active < time.time() - session_timeout_minutes.

Reverse Proxy Policy

The gateway serves as a secure shield between public networks and downstream microservices. It implements strict validation to block HTTP smuggling, header injection, and cookie leakages.

Case-Insensitive Header Stripping

To prevent malicious clients from attempting to bypass gateway-level authentication by supplying pre-forged identity headers, IntraGate strips all headers starting with X-Gateway-User- case-insensitively before proxying the request downstream:

Header Stripping (app/proxy.py)
# Strip client-supplied user information headers case-insensitively
headers_to_remove = [k for k in client_headers.keys() if k.lower().startswith("x-gateway-user-")]
for k in headers_to_remove:
    del client_headers[k]

Cookie Isolation

To prevent upstream applications from gaining access to the main gateway session token (intragate_sid), the proxy engine inspects the forwarded Cookie header and deletes gateway-related cookies before sending the request upstream.

Proxy Schemes & TLS Verification

For each registered downstream application, the administrator can configure whether SSL certificates should be verified (tls_verify). This supports local apps using self-signed development certificates without compromising global routing safety.

Admin Security Controls

Because the Admin Panel controls application registries and routing schemes, it has been hardened with advanced defense mechanisms.

Brute-Force & Rate-Limiting Lockout

Local admin logins are protected by an IP-based lockout system. Failed logins are recorded in the database, triggering exponential delays:

  • Lockout Threshold: After 5 failed attempts, the IP is locked out.
  • Response Code: Locked-out IPs receive 429 Too Many Requests with an active countdown.
  • Lockout Duration: Starts at 15 minutes and scales exponentially on subsequent failures.

Upload Validation & Magic Bytes

When uploading a corporate logo in Portal Settings, the panel executes strict server-side validation to prevent shell uploads (e.g. SVG/HTML payloads) disguised as images:

  1. File Size & Name: Size is restricted, and file extension is normalized.
  2. Dimensions Check: Image width and height are read using PIL and verified to be ≤ 400x400 pixels.
  3. Magic Bytes Integrity: The file content is opened and verified to ensure it is a valid, un-corrupted binary image of type PNG, JPEG, or GIF.

Admin Features & Settings Reference

This section provides a granular, field-by-field breakdown of every setting, configuration panel, and security control inside the IntraGate Admin User Interface.

1. Initial Setup Wizard

When the application is booted for the first time with an empty PostgreSQL database, the gateway enters Setup Mode. The main portal routes will redirect to the setup page. The admin must configure the initial credentials:

  • Administrator Username: The unique username used to log in to the admin panel. Avoid simple terms like "admin".
  • Administrator Password: Must be at least 8 characters long. The password is hashed on the server side using the industry-standard bcrypt algorithm with 12 salt rounds before being written to the database.

Once the administrator account is created, Setup Mode is deactivated and the portal transitions to production mode, requiring Entra ID login for general users.

2. Two-Factor Authentication (MFA / TOTP)

To secure the admin panel against credential theft, admins can enable Multi-Factor Authentication based on RFC 6238 Time-Based One-Time Passwords (TOTP):

  • Secret Generation: When setup is initiated, the server generates a cryptographically secure 32-character base32 secret key.
  • QR Code Enrollment: The secret is encoded into a URI (e.g. otpauth://totp/IntraGate:username?secret=...) and presented as a high-contrast QR code on the dashboard. Scan this using Google Authenticator, Microsoft Authenticator, Aegis, Bitwarden, or any compatible client.
  • Verification & Activation: To prevent lockout due to misconfiguration, the admin must enter their login password and the current 6-digit TOTP token. The server verifies the token before setting totp_enabled = True in the database.
  • Deactivation: Can only be disabled by providing the admin's password and a valid current TOTP token.

3. Application Registry Configuration

The Application Registry defines the downstream web applications protected by IntraGate. To register an application, click + Add Application and configure the following parameters:

Setting / Field Format & Constraints Description & Behavior
Application Name Alphanumeric text (1 to 100 characters) The user-friendly name displayed on the portal home screen landing cards (e.g., Grafana Analytics).
Route Slug Lowercase, hyphens, alphanumeric (min 1 char)
Regex: ^[a-z0-9]+(-[a-z0-9]+)*$		 The unique URL path prefix under which the application is served. For example, a slug of grafana routes all public traffic under https://intragate.dev/app/grafana to the target service. If left empty, it is generated automatically from the name.
Upstream URL Valid URL string (HTTP/HTTPS scheme)
Example: http://10.0.5.12:3000		 The target address of the internal web application. Can specify hostname, internal DNS names, or IP addresses with custom ports.
Allowed Group Object ID Valid UUID format (36 characters)
Example: ba805f21-2393-4593-92f2-91cfb9178718		 The exact Object ID of the Microsoft Entra ID security group whose members are authorized to access this application. Users who do not belong to this group will be denied access and shown a clean 403 authorization screen.
Verify TLS Certificates Boolean toggle (Enabled / Disabled) Enabled: The gateway validates the upstream SSL/TLS certificate against the host system's trust store. Must be active for production traffic to prevent man-in-the-middle attacks.
Disabled: Bypasses TLS chain validation. Intended for development/staging nodes using self-signed or expired internal certificates.

4. Portal Branding & Theme Settings

This panel allows tailoring the user-facing landing portal to match corporate brand guidelines. All style parameters undergo strict input validation:

  • Organization Name: Displays in the main page header and browser tab title.
  • Subtext / Description: Secondary text block displaying welcome messages or compliance notices to users.
  • Footer Copyright Text: Text block at the bottom of the landing dashboard.
  • Primary & Accent Hex Colors: Must be valid 6-character hex color codes starting with a hash (e.g., #1F4E79). Verified on save against the regex pattern ^#[0-9A-Fa-f]{6}$ to prevent injection attacks.
  • Custom Logo Upload:
    • Dimensions Constraint: The uploaded image must be less than or equal to 400x400 pixels. Read and verified using the Pillow library.
    • Safe Formats: Must have a file extension of .png, .jpg, .jpeg, or .gif.
    • Magic Bytes Validation: The server opens the raw binary stream and reads the file headers to guarantee the image's binary integrity. Executable code or scripts hidden inside the image file are rejected immediately.
    • Serving Scheme: Custom logo files are served securely via a custom endpoint /uploads/{filename} that returns the file with Content-Security-Policy: default-src 'none' and X-Content-Type-Options: nosniff headers, mitigating script execution or HTML injection in uploaded media.

5. Audit Logging & Report Exports

All sensitive operations within the IntraGate engine are logged to the PostgreSQL database for security compliance and post-incident forensic investigation. The logs can be searched, filtered, and exported:

  • Logged Event Types:
    • login: Successful Entra ID authentication and local admin logons.
    • login_failed: Failed local admin attempts, including invalid username, password, or TOTP code.
    • lockout: Source IP or username brute-force lockout events.
    • logout: Explicit user and administrator logouts.
    • session_cleanup: Background execution of the session pruning routine.
    • config_update: Updates to Entra ID, portal settings, or registry entries.
  • CSV Export: Downloads a full comma-separated file of all filtered log records. Suitable for ingestion into SIEM tools like Splunk or Elastic.
  • PDF Export: Generates an executive security report PDF containing a stylized table of audit logs, timestamps, user identifiers, IP addresses, and actions.

Entra ID SSO Setup

This section provides a step-by-step tutorial on registering IntraGate inside the Microsoft Entra ID (formerly Azure Active Directory) Portal to configure Single Sign-On.

Step 1: Create App Registration

  1. Log in to the Azure Portal as an Application Administrator or Global Administrator.
  2. Search for and select Microsoft Entra ID from the services list.
  3. In the left-hand navigation pane, select App registrations and click + New registration.
  4. Configure the registration fields as follows:
    • Name: Input a descriptive name (e.g., IntraGate SSO Gateway).
    • Supported account types: Choose Accounts in this organizational directory only (Single tenant).
    • Redirect URI: In the dropdown, select Web and input your exact gateway callback endpoint:
      https://your-portal-domain.com/auth/callback (Ensure this uses HTTPS in production).
  5. Click Register.

Step 2: Enable ID Token Flow

  1. Under the registered app menu, select Authentication (under the *Manage* subgroup).
  2. Scroll down to the Implicit grant and hybrid flows section.
  3. Check the box for ID tokens (used for implicit and hybrid flows).
    Note: This is required by the OIDC validation middleware to authenticate the user profile signature securely.
  4. Click Save at the top of the pane.

Step 3: Generate Client Secret

  1. Navigate to Certificates & secrets -> Client secrets tab in the left-hand menu.
  2. Click + New client secret.
  3. Provide a description (e.g. IntraGate Production Secret) and choose an expiration period (e.g. 12 months).
  4. Click Add.
  5. Important: Copy the string in the Value column immediately. This value is hidden forever after navigating away. (Do *not* copy the Secret ID).

Step 4: Grant Microsoft Graph API Permissions

  1. Navigate to API permissions in the left pane.
  2. Under *Configured permissions*, click + Add a permission and select Microsoft Graph.
  3. Choose Delegated permissions.
  4. Search and select the following OIDC scopes:
    • openid: Grants access to sign users in.
    • profile: Grants access to read user names.
    • email: Grants access to read user email addresses.
    • User.Read: Standard permission to read the signed-in user's profile and group memberships.
  5. Click Add permissions.
  6. (Recommended) If logged in as Tenant Administrator, click Grant admin consent for [Company] to prevent users from seeing consent prompts.

Step 5: Configure Security Groups Claim

IntraGate authorizes user access based on group membership. To send the security group IDs in the token, you must configure a groups claim.

  1. In your application registration page, select Token configuration from the left-hand navigation pane.
  2. Click + Add groups claim.
  3. In the popup drawer, configure the options:
    • Select Security groups (this covers standard security groups).
    • (Optional) You can also select Directory roles and All groups if required by your access control configuration.
  4. Expand the dropdown for Customize token properties by type (Web, ID, Access):
    • Select Group ID for ID and Access tokens. This ensures the raw Azure Object ID (UUID format, e.g. ae8dbe8c-f030-4f5c-8f56-060bccd6ace4) is emitted, which corresponds directly to the configured Group ID in IntraGate.
  5. Click Add.
Understanding Group Overage Claims & API Fallback

When a user belongs to many groups, the list of group IDs can exceed the token size limit (typically more than 200 groups for SAML, or 6 groups for implicit JWT tokens). Under these circumstances, Microsoft Entra ID omits the group IDs from the token and adds an overage claim:

"_claim_names": {"groups": "src1"}

IntraGate is engineered to handle group overage gracefully. When an overage claim is detected in the claims payload, the gateway automatically connects to the Microsoft Graph API using the endpoint https://graph.microsoft.com/v1.0/me/memberOf to retrieve the user's transitive group memberships. This lookup runs asynchronously and transparently to the user, but requires the User.Read delegated permission to be consented in Step 4.

Step 6: Configure Gateway Settings

From the App registration's **Overview** page, copy the following values to configure in the IntraGate admin portal:

  • Application (client) ID (UUID format)
  • Directory (tenant) ID (UUID format)

Log in to the IntraGate Admin Panel (via localhost SSH tunnel), go to **Entra ID Configuration**, and input these values alongside the Client Secret and Redirect URI. Once saved, these parameters are encrypted using GATEWAY_ENCRYPTION_KEY and persisted in the database.

Troubleshooting & FAQ

Database connection fails at startup
Problem: Gateway container fails to start, displaying database connection errors.
Solution: The PostgreSQL database container might take a few seconds to initialize on the first run. The gateway will automatically retry connection 5 times. Ensure that POSTGRES_PASSWORD matches in both the postgres container definition and the database connection URL.
IP Address Spoofing Audit Warn
Problem: Log messages indicate audit entries recording IP mismatches.
Solution: Ensure that your upstream load balancer (e.g. Traefik, NGINX) is listed in the TRUSTED_PROXIES environment variable. If not listed, IntraGate will ignore the X-Forwarded-For header to prevent IP spoofing attacks.

Common FAQ

Q: Why can't I reach the Admin Panel on my public IP?
A: For security reasons, the admin panel binds strictly to 127.0.0.1:8585. You must create an SSH tunnel (e.g. ssh -L 8585:127.0.0.1:8585 user@server) to access the panel locally on your workstation.

Q: How do I rotate session signing keys?
A: Generate a new key and update the GATEWAY_SECRET_KEY variable. Note that rotating this key will immediately invalidate all existing user sessions, prompting users to re-authenticate. Rotating this key does NOT affect encrypted values in the database, which rely on GATEWAY_ENCRYPTION_KEY.
